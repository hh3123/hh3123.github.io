Health checks that actually catch failures

2026-09-28

A health probe is only useful if it fails when the service is broken.

Most containers ship a liveness probe that opens a TCP connection. That tells you the process is listening — not that it can serve a request. A worker whose database pool is exhausted, or whose event loop is blocked, will happily accept the socket and then time out on every real call.

Probe the request path

Expose a dedicated endpoint that exercises the same dependencies the service needs to do its job, and keep it cheap: one query, one cache read, with a short timeout.

async def health():
    await db.fetchval("select 1")
    await cache.ping()
    return {"ok": True}

Separate liveness from readiness

Liveness should answer "is this process wedged?" and nothing else. Readiness answers "should traffic come here?". Mixing them means a slow dependency restarts a perfectly good process.

  • /livez returns 200 unless the event loop is stuck.
  • /readyz checks dependencies and may fail transiently.
  • Restart only on liveness failure, drain only on readiness failure.

Timeouts are part of the contract

Give the probe a deadline shorter than the orchestrator's timeout, so you return a structured failure instead of being killed mid-check. A probe that hangs is indistinguishable from a dead process.
